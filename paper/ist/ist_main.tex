\title{A Comparability Protocol for Benchmarking Relational Database
  Access Layers in Express.js}

\author[ug]{Mateusz Miotk\corref{cor1}}
\ead{mateusz.miotk@ug.edu.pl}
\cortext[cor1]{Corresponding author.}
\affiliation[ug]{organization={Faculty of Mathematics, Physics and Informatics,

\begin{abstract}
\textbf{Context:} Benchmarks of relational database access layers inform technology-selection
decisions, yet can time implementations that returned different results, or report latency at unequal
proximity to saturation. Whether the compared configurations are comparable is rarely established.
\textbf{Objectives:} We propose an executable protocol for deciding when configured implementations
are comparable for a stated estimand, and what their measurements support, then exercise it in one
empirical instantiation rather than validating it independently.
\textbf{Methods:} The protocol requires task-derived read checks, cross-implementation equivalence,
post-write state validation, a predeclared configuration-selection policy, and separate capacity and
latency operating points. An open-source Express.js experiment compares nine policy-selected configurations
and two tuned native references across PostgreSQL, MySQL, and five access patterns in a 25-run
randomized-block campaign, with a reduced second same-host campaign testing rank stability and a
single-rater audit of nine external benchmarks.
\textbf{Results:} The widest spread is the tested deep fetch, $7.01\times$ on PostgreSQL and
$5.12\times$ on MySQL; forcing common SQL through raw facilities in a separate ten-run campaign
leaves $1.71\times$ and
$2.03\times$, a compound contrast isolating no single mechanism. High-load and matched-utilization p99 are different
quantities, not one optimized against the other; the matched-utilization figures rest on five runs
and are secondary. Four cross-stack rank reversals recur in both campaigns, all
involving the one treatment whose MySQL driver differs, and no other pair clears the same bar,
while whole-ordering agreement stays imperfect. Only that treatment reverses durably at the
stated bar, and the experiment does not identify the DBMS as the cause.
\textbf{Conclusion:} The protocol is a candidate: a structured, auditable proposal with one worked
instantiation rather than a validated methodology, and supports no universal ranking or library-intrinsic overhead estimate.
Its audit has one rater, the adapters lack independent review, and both campaigns share one host, so
independent applicability remains untested.
\end{abstract}

\section*{Data availability}
The public repository is available at
\url{https://github.com/mmiotk/express-db-access-performance}. The complete revision artifact is
archived as release v1.13.15, which the concept DOI
\url{https://doi.org/10.5281/zenodo.21313858} resolves to~\cite{miotk2026artifact}; the Zenodo record
also carries an immutable per-version DOI for that release.
A reproducibility summary --- versions, requirements, run commands, resources needed, and which
results the harness regenerates automatically from the archived raw data --- is in Supplement
Table~S31 and \texttt{REPRODUCE.md}. \textbf{Exact reproduction requires the reference engines}
(PostgreSQL~18.4 and MySQL~9.7.1) via the user-space conda path documented there; the convenience
Docker path pins the same engine versions but uses relaxed durability in a containerized topology, so
it reproduces the workflow, not the headline default-durability insert numbers. A machine-readable
encoding of the protocol ships as \texttt{protocol-checklist.yaml}. Reproduction status is separated
explicitly: author-run isolated reconstructions verified the archived JSON hashes and regenerated the
committed tables byte-for-byte without starting either DBMS (dates and counts in Supplement
Table~S31). Neither is independent reproduction nor a re-execution of the current measurements, and
neither is described as such.
